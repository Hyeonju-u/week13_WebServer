# 3단계: 이벤트 루프 1개 + 정적 서빙

> 결정: 2026-11-24 대화 (Notion "웹 서버 요구분석"에 같은 내용 기록)
> 관련 R: R1a, R1f, R3c, R3d, R4a, R6a, R6b (+ 1단계 파서, 2단계 정적 응답 재사용)
> 완료 기준 (구현 단계 계획): curl·브라우저로 정적 파일을 받음, 동시 50개 전부 200, 느린 손님이 있어도 다른 손님은 정상. 아래 테스트 목록 전부 통과, ASan에서 누수·잘못된 접근 0.

## 1. 범위

- **한다:** 서버 실행 파일, non-blocking 소켓, epoll 루프 1개, 연결 진행 카드(상태 기계), keep-alive, 부분 읽기·쓰기, 파일 조각 전송, 끊김 정리, 타임아웃, lingering close, 접근·오류 로그, SIGPIPE 무시
- **안 한다:** 라우팅·프록시(4단계), 루프 N개·accept 전담 스레드(5단계), SIGINT/SIGTERM 셧다운(6단계), 설정 파일(D10, 항목이 다 모인 뒤)
- 이 단계는 모든 요청을 정적 요청으로 본다 (라우터는 4단계).

## 2. 흐름 (연결 하나)

```
accept → 카드 만들기 → [헤더 읽기] ─헤더 완성→ parse_request_head
   BAD → 오류 응답 + close 예약 (B31)
   OK  → open_static_file (POST면 405) → 응답 헤더 → [응답 쓰기: 헤더 → 파일 조각]
응답 끝 → close 예약이면 [lingering] → close
        → 본문이 남았으면 [본문 버리기] (L11, L21) → 아래 버퍼 확인
        → 아니면 우리 버퍼부터 확인 (L13) → 완성된 요청이 있으면 바로 처리
                                          → 없으면 [keep-alive 대기]
```
