# C 웹서버 + 리버스 프록시

C와 POSIX API만 사용한 HTTP/1.1 웹서버입니다. 외부 HTTP·이벤트 루프 라이브러리를 쓰지 않았고,
정적 파일 서빙과 리버스 프록시(경로 라우팅, Round-Robin)를 하나의 이벤트 루프에서 처리합니다.

발표·설명용 문서는 [docs/overview.md](docs/overview.md)에 있습니다.

## 빌드와 실행

```bash
make                # build/webserver
make test           # 단위 + 기능 + 가혹 조건(빠른 판)
```

```bash
build/webserver --root www --port 8080 --config proxy.conf --log-level info --max-connections 10000
```

| 옵션 | 뜻 | 기본값 |
|---|---|---|
| `--root` | 정적 파일 루트 폴더 (필수) | - |
| `--port` | 포트 | 8080 |
| `--config` | 리버스 프록시 설정 파일. 없으면 정적 파일만 서빙 | 없음 |
| `--log-level` | `error` / `info` / `debug` | info |
| `--max-connections` | 최대 동시 연결 수 | 10000 |

설정 파일은 한 줄에 규칙 하나입니다.

```
route /api 127.0.0.1:8001 127.0.0.1:8002 127.0.0.1:8003
route /api/admin 127.0.0.1:8004
connect_timeout 3
response_timeout 10
```

- 경로는 조각 단위로 맞춥니다. `/api`는 `/api`, `/api/users`와 맞고 `/apix`와는 맞지 않습니다.
- 규칙이 겹치면 가장 긴 경로가 이깁니다. 백엔드에는 손님이 보낸 URI(쿼리 포함)를 그대로 넘깁니다.
- 어떤 규칙에도 맞지 않는 요청은 정적 파일로 처리합니다.
- 형식이 틀리거나 백엔드 주소를 해석할 수 없으면 서버가 시작되지 않습니다.

## 데모 시연 (터미널 하나로 실행)

백엔드는 "프록시가 요청을 넘겨 받을 뒤쪽 서버"입니다. 시연용으로 파이썬 기본 웹서버 두 대를 포트 9001, 9002에 띄우고, 어느 쪽이 답했는지 구분되게 파일 내용을 다르게 둡니다. 웹서버 빌드와는 무관합니다.

### 1. 준비와 시작

```bash
make clean && make
mkdir -p /tmp/demo/b1/api /tmp/demo/b2/api && echo backend-1 > /tmp/demo/b1/api/hello && echo backend-2 > /tmp/demo/b2/api/hello
(cd /tmp/demo/b1 && python3 -m http.server 9001 --bind 127.0.0.1 >/dev/null 2>&1 &)
(cd /tmp/demo/b2 && python3 -m http.server 9002 --bind 127.0.0.1 >/dev/null 2>&1 &)
echo "route /api 127.0.0.1:9001 127.0.0.1:9002" > /tmp/demo/demo.conf
build/webserver --root www --port 8080 --config /tmp/demo/demo.conf > /tmp/demo/server.log 2>&1 &
```

### 2. 정확성: 정적 파일, 오류 코드, 보안

```bash
curl -i localhost:8080/                                   # 200, 헤더 확인
curl -I localhost:8080/index.html                         # HEAD: 본문 없음
curl -i --path-as-is localhost:8080/../etc/passwd         # 404 (경로 탈출 차단)
curl -i localhost:8080/.git/config                        # 404 (숨김 경로)
curl -i -X POST -d x=1 localhost:8080/                    # 405 + Allow: GET, HEAD
curl -i -H "Transfer-Encoding: chunked" -H "Content-Length: 5" -d x localhost:8080/   # 400 (Smuggling 방지)
```

### 3. 리버스 프록시와 Round-Robin

```bash
for i in 1 2 3 4; do curl -s localhost:8080/api/hello; done   # backend-1, backend-2 번갈아
```

### 4. 동시성: 느린 손님이 다른 손님을 막지 않는다

```bash
# 요청을 끝내지 않고 붙들고 있는 손님 5명
for i in 1 2 3 4 5; do (printf 'GET / HTTP/1.1\r\nHost: x\r\n'; sleep 8) | nc localhost 8080 >/dev/null & done
sleep 1
curl -s -o /dev/null -w "정상 손님: %{http_code}, %{time_total}초\n" localhost:8080/   # 바로 200
wrk -t2 -c1000 -d5s --latency http://localhost:8080/index.html                        # 동시 연결 1,000개
```

### 5. 백엔드 장애

```bash
pkill -f "http.server 9001"; for i in 1 2 3; do curl -s localhost:8080/api/hello; done   # 살아 있는 쪽으로만
pkill -f "http.server 9002"; curl -i localhost:8080/api/hello                            # 502
```

### 6. 종료와 정리

```bash
pkill -INT -f "build/webserver"                               # 우아한 종료
cat /tmp/demo/server.log                                      # 시작, 종료 로그
pkill -f "http.server 900"; rm -rf /tmp/demo
```

## 파일 구성

| 파일 | 역할 |
|---|---|
| `src/main.c` | 옵션 해석, 시작·종료 |
| `src/server.c` | 이벤트 루프, accept, 손님 연결의 읽기·쓰기, 타임아웃, 우아한 종료 |
| `src/proxy.c` | 백엔드 연결, 요청 전송, 응답 중계, 배압 |
| `src/proxy_message.c` | 백엔드로 보낼 요청과 응답 헤더 만들기, 백엔드 응답 파싱 (소켓과 분리된 순수 함수) |
| `src/proxy_config.c` | 설정 파일 해석, 경로 라우팅 |
| `src/http_parser.c` | 요청 파서 (소켓과 분리된 순수 함수) |
| `src/http_response.c` | 상태 코드 표, 응답 헤더·오류 페이지 |
| `src/static_file.c` | 경로 검사와 파일 열기 (`openat` + `O_NOFOLLOW`) |
| `src/mime.c` | 확장자 → MIME 타입 표 |
| `src/event.c` | kqueue(macOS) / epoll(Linux) 공통 래퍼. `#ifdef`는 이 파일에만 있음 |
| `src/timer_heap.c` | 연결별 마감 시각을 관리하는 최소 힙 |
| `src/buffer.c` | 길이를 가진 바이트 버퍼, 서버 전체 합계 상한 |
| `src/connection.c` | 연결 상태 구조체 |
| `src/signals.c` | SIGPIPE 무시, SIGINT·SIGTERM 종료 플래그 |
| `src/settings.h` | 상한·타임아웃 상수 |
| `tests/` | 단위(C), 기능·가혹 조건(Python), 벤치마크 |

## epoll 동시성 모델을 고른 이유 (CON-16)

I/O 멀티플렉싱 이벤트 루프 하나(macOS는 kqueue, Linux는 epoll)를 씁니다.
가치의 순서가 정확성 > 안정성 > 성능이고, 수천 명이 동시에 붙어도 메모리를 적게 써야 하기 때문입니다.

| | 이벤트 루프 (선택) | 스레드풀 | 요청마다 fork |
|---|---|---|---|
| 동시에 붙들 수 있는 손님 | 연결 수만큼 (구조체 하나씩) | 스레드 수로 고정 | 프로세스 수 |
| 느린 손님·keep-alive 유휴 손님 | 구조체 하나만 차지 | 스레드를 통째로 붙잡음 | 프로세스를 통째로 붙잡음 |
| 연결당 메모리 | 구조체 320바이트 + 필요할 때 4KB 버퍼 최대 둘 | 스레드 스택(보통 수백 KB~MB) | 프로세스 전체 |
| 공유 데이터 경쟁 | 없음 (단일 스레드) | 있음 (잠금 필요) | 프로세스끼리 분리 |
| 재현·테스트 | 같은 입력에 같은 결과 | 실행 순서에 따라 달라짐 | 비교적 쉬움 |

대가도 있습니다. 한 요청의 처리가 오래 걸리면 모든 손님이 멈추므로, 루프 안에서는 절대 기다리지 않도록 만들었습니다
(주소 해석은 시작 때 한 번, `connect`는 non-blocking, 파일은 64KB씩). CPU 코어를 하나만 쓴다는 한계도 있습니다.

## 설정값과 이유 (NFR-12)

모두 `src/settings.h`의 상수입니다. CLI로 바꿀 수 있는 것은 포트, 루트, 설정 파일, 로그 레벨, 최대 연결 수와
설정 파일의 두 타임아웃뿐입니다.

| 항목 | 값 | 이유 |
|---|---|---|
| 요청 라인 상한 | 8KB | 일반 서버(nginx 등)가 쓰는 크기. 넘으면 414 |
| 헤더 전체 상한 / 개수 | 16KB / 100개 | 쿠키가 큰 정상 요청은 통과시키고 헤더 폭탄은 막음. 넘으면 431 |
| 본문 상한 | 1MB | 연결 1만 개가 모두 큰 본문을 보내도 메모리를 보호. 넘으면 본문을 받기 전에 413 |
| 입력 버퍼 시작 크기 | 4KB | 대부분의 요청이 작아서 연결마다 큰 버퍼를 잡지 않으려고 |
| 버퍼 합계 상한 | 512MB | 서버 전체 메모리 보호. 넘기는 요청은 503 후 닫음 |
| 요청 읽기 타임아웃 | 15초 (갱신 안 함) | 1바이트씩 보내며 붙잡는 Slowloris가 타이머를 계속 리셋하지 못하게 |
| Keep-Alive 유휴 타임아웃 | 5초 | 한가한 연결이 fd를 오래 차지하지 않게 |
| 최대 동시 연결 수 | 10,000 | 요구사항. 상한에 닿으면 accept를 멈추고 커널 대기 줄에 둠 |
| 파일 전송 단위 / 프록시 배압 기준 | 64KB | 큰 파일을 통째로 메모리에 올리지 않고, 느린 손님 때문에 버퍼가 끝없이 커지지 않게 |
| 우아한 종료 대기 | 5초 | 보내던 응답을 마칠 시간을 주되 무한정 기다리지 않게 |
| 백엔드 연결 / 응답 타임아웃 | 3초 / 10초 (설정 파일) | 죽은 백엔드를 빨리 건너뛰고, 느린 백엔드는 마지막 수신 후 10초에 504 |
| 한 바퀴 accept 최대 | 64개 | 접속이 몰려도 이미 연결된 손님의 처리가 밀리지 않게 |
| 로그 레벨 기본값 | info | 정의서가 팀 결정으로 남긴 항목. 부하 테스트는 `error`로 측정 |

## 테스트 실행 방법 (TST-07)

| 명령 | 내용 |
|---|---|
| `make test` | 단위 테스트 + 기능 테스트 + 가혹 조건(빠른 판). 모든 테스트를 명령 하나로 다시 돌린다 |
| `make unit-test` | `tests/test_*.c` (assert, 외부 테스트 라이브러리 없음) |
| `make functional-test` | `tests/functional_test.py` (curl 대신 원시 소켓으로 응답 코드 요약표를 하나씩 확인) |
| `make stress-test` | `tests/stress_test.py` 정식 규모 (TST-11~19). 약 15분 |
| `make long-test` | 30분 장시간 실행 (TST-20) |
| `make bench` | `tests/bench.sh` wrk 부하 테스트 (연결 100 → 1,000 → 10,000, 단계마다 30초 × 3회) |
| `make asan` / `make ubsan` | 검사용 빌드. 성능 수치는 이 빌드로 재지 않는다 (TST-06) |

테스트용 백엔드 B는 `tests/backend_b.py`(Python, `socket` 모듈만 사용)이고, 웹서버 빌드에는 들어가지 않습니다.
원본 출력은 `tests/results/`에 있습니다.

메모리는 macOS가 해제한 페이지를 RSS에 계속 세기 때문에 `footprint`(실제 점유량)로 쟀습니다. 연결을 1만 개 열었다 닫으면
점유량이 한동안 높게 남지만 같은 부하를 한 번 더 돌려도 늘지 않았고(TST-11, 15/16, 17은 "반복해도 늘지 않음"으로 판정)
`leaks`가 0건이라 누수가 아니라 할당자가 쥐고 있는 조각으로 판단했습니다. 가벼운 시나리오(TST-12, 13, 14, 18, 19)는 시작값 + 4MB 이내로 돌아왔습니다.
상한 초과 시나리오(wrk로 12,000개 시도)는 끝난 뒤 25.6MB가 남았고, 이 항목만 시작값 + 70MB 이내라는 느슨한 기준으로 판정했습니다
(이 시나리오는 같은 부하를 반복해 보지 않았습니다).

### 부하 테스트 (wrk, `tests/results/wrk_*.txt`)

정적 파일(약 1.8KB) 한 개를 가져가는 요청, 단계마다 30초 × 3회의 중앙값입니다. 로그 레벨은 `error`입니다.

| 동시 연결 | 처리량 (req/s) | p50 (ms) | p99 (ms) | wrk 에러 합계 |
|---|---|---|---|---|
| 100 | 67,539 | 1.47 | 1.61 | 0 |
| 1,000 | 66,269 | 15.03 | 16.19 | 0 |
| 10,000 | 58,298 | 114.15 | 177.14 | 22,699 (읽기 에러) |

연결 10,000 단계의 wrk 읽기 에러는 서버가 연결을 닫아서 생긴 것이 아니라고 판단합니다.

- 디버그 로그로 같은 부하를 돌렸을 때 서버가 연결을 닫았다는 기록이 한 건도 없었습니다 (타임아웃, 읽기·쓰기 실패 모두 0).
- 타임아웃도 연결 종료 로직도 없는 최소 kqueue 서버(응답만 돌려주는 40줄짜리)에 같은 wrk를 붙이면 같은 에러가 납니다
  (5,000연결에서 1,090건, 10,000연결에서 3,621건 / 15초).
- 같은 10,000개 연결을 Python 클라이언트로 붙여 응답 내용을 하나하나 검증했을 때(TST-11)는 오류가 0건이었습니다.

다만 에러의 정확한 원인(wrk, macOS 루프백 중 어느 쪽인지)은 확인하지 못했습니다.

## 알려진 한계

- 응답을 받아 가지 않는 손님에게는 쓰기 타임아웃이 없습니다 (정의서에 없음). 그런 연결은 fd를 계속 차지합니다. 종료할 때는 5초 뒤 정리됩니다.
- 일반 파일 `read()`는 non-blocking이 아니라서 디스크가 느리면 64KB를 읽는 동안 루프가 잠시 멈출 수 있습니다 (정의서 13장).
- 느린 망(약 50KB/s 미만)에서 1MB에 가까운 본문은 15초 요청 읽기 타임아웃에 걸릴 수 있습니다 (정의서 13장).
- 루트 안을 가리키는 심볼릭 링크도 TOCTOU 방지를 위해 403으로 거절합니다 (정의서 13장).
- 본문이 큰 요청을 413 등으로 거절할 때 손님이 본문을 계속 보내는 중이면, 이미 도착한 데이터만 버리므로 오류 응답이 손님에게 닿기 전에 RST를 만날 수 있습니다. `Expect: 100-continue`를 쓰는 손님(curl의 큰 POST)은 이 문제 없이 413을 받습니다.
- 이벤트 루프가 하나라 CPU 코어를 하나만 씁니다.
- HTTP/1.1만 지원하고 TLS(HTTPS)는 없습니다.
- 요청 본문은 `Content-Length`만 받습니다. `Transfer-Encoding: chunked` 요청은 501로 거절합니다. 본문 상한은 1MB입니다.
- 백엔드와는 요청마다 새 연결을 맺습니다. 연결 재사용(keep-alive 풀)이 없습니다.
- 백엔드 상태 검사가 없습니다. 죽은 백엔드는 연결을 시도해 보고 실패하면 건너뜁니다.
- 백엔드가 101(프로토콜 전환, WebSocket 등)을 보내면 502로 처리합니다.
- Range, 조건부 요청(ETag 등), 압축은 지원하지 않습니다.
- wrk 10,000 연결에서 읽기 에러가 나옵니다. 위 "부하 테스트"에 근거를 적었지만 원인은 확인하지 못했습니다.

## 검증하지 못한 것

| 항목 | 상황 |
|---|---|
| Linux에서 빌드와 실행 | Docker(Ubuntu 22.04, gcc 11.4, x86_64 에뮬레이션)에서 빌드, 단위 테스트 7개, 기능 테스트 164/164가 통과했습니다. 실제 WSL과 Linux 실물에서는 돌리지 않았습니다 |
| ASan·UBSan | Linux 컨테이너에서 `make asan` 빌드로 기능 테스트 164/164를 돌렸고 sanitizer 오류는 없었습니다. 이 개발 컴퓨터(macOS)에서는 ASan이 `main` 이전에 멈춰서 UBSan, Guard Malloc, `leaks`를 썼습니다. ASan에서는 해제 격리 영역 때문에 메모리 증가 검사가 실패해 보이므로 `ASAN_OPTIONS=quarantine_size_mb=0`을 줘야 합니다 |
| Linux에서의 가혹 조건·부하 테스트 | TST-13, 15, 17, 18은 통과했습니다. wrk가 필요한 TST-12, 14, 19, 부하 측정, 30분 장시간 테스트는 Linux에서 돌리지 않았습니다 |
| 테스트 도구의 Linux 지원 | `tests/harness.py`가 macOS 명령(`footprint`, `lsof`, `leaks`)을 써서 Linux에서는 그대로 돌아가지 않습니다. 위 Linux 결과는 컨테이너 안 사본에서 `/proc` 기반으로 바꿔 얻은 것이고, 저장소의 도구는 아직 고치지 않았습니다 |
| 백엔드 연결 타임아웃 | 연결이 안 되는 주소(`192.0.2.1`)로 504가 1.0초에 나오는 것을 확인했습니다. 네트워크에 따라 즉시 실패하면 재현되지 않을 수 있습니다 |
