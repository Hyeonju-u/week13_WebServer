# 멀티 이벤트 루프 결정 기록

## 결정 (M, 2026-11-25)

| # | 결정 | 대가 / 남는 구멍 |
|---|---|---|
| M1 | 루프마다 같은 포트로 listen 소켓을 열고 SO_REUSEPORT로 커널이 연결을 나눔. accept 전담 스레드는 만들지 않음 | 커널이 해시로 고정 배정해서 한 루프에 몰려도 옮길 수 없음. macOS는 분배 보장 안 됨 → M2 |
| M2 | 루프 수 기본값 sysconf(_SC_NPROCESSORS_ONLN), --loops N(1~256, 벗어나면 사용법 출력 후 종료 코드 2)으로 덮어씀. macOS(__APPLE__) 빌드는 기본 1. 시작 로그에 루프 수 | docker run --cpus 제한은 sysconf에 안 보임 → README에 --loops로 맞추라고 적음 |
| M3 | buffer.c 메모리 합계(NET-12 512MB)는 C11 원자 변수 하나를 모든 루프가 같이 셈. 먼저 atomic_fetch_add, 상한을 넘으면 atomic_fetch_sub로 되돌리고 실패 | 버퍼를 늘릴 때마다 원자 연산 1번 |
| M4 | 최대 연결 수는 서버 전체 합계를 원자 변수로 셈 (M3과 같은 방식). 각 루프는 "전체가 찼나"만 보고 accept를 멈추고, resume_accepting에서 다시 받음. raise_fd_limit은 시작 때 한 번, 전체 기준 | 연결을 받을 때·닫을 때 원자 연산 1번 |
| M5 | (2026-11-25 수정) upstream_t는 서버 전체에 하나 만들어 모든 루프가 같이 씀. Round-Robin 차례는 규칙마다 원자 변수 하나(atomic_fetch_add로 번호표), 빠진 시각은 백엔드마다 원자 변수(atomic_store / atomic_load). 잠금은 쓰지 않음. 처음 결정(루프마다 따로)은 기존 Round-Robin 순서 테스트와 LB-4(첫 요청만 재시도)를 깨서 바꿈 | 프록시 요청마다 원자 연산 1~2번. "빠졌나 보고 고르기"는 한 덩어리가 아니라서, 한 루프가 살아 있다고 읽은 직후 다른 루프가 빼면 그 요청은 한 번 더 시도함 (실패하면 기존처럼 다음 백엔드로 재시도) |
| M6 | 종료: 핸들러는 그대로 두고 shutdown_flag를 volatile sig_atomic_t에서 atomic_int로 바꿈. 각 루프는 WAIT_MAX_MS(1초) 안에 깨어나 확인하고 자기 listen 소켓을 닫고 기존 종료 절차를 밟음. 메인 스레드는 루프 스레드를 만들고 pthread_join으로 모두 기다린 뒤 server_t들 → 설정 순서로 정리 | 루프마다 종료 시작이 최대 1초 어긋남 (최대 약 6초, docker stop 10초 안). 닫은 listen 소켓 대기열의 연결은 끊김 |
| M7 | (2026-11-25 수정) 루프끼리 같이 쓰는 쓰기 값은 M3·M4·M6과 M5의 차례·빠진 시각뿐이고 모두 원자 변수. 설정(proxy_config), 루트 경로, 로그 레벨은 스레드를 만들기 전에 정하고 읽기만 함. 연결 하나는 자기를 받은 루프만 만짐 (루프 사이에 연결을 넘기지 않음) | — |
| M8 | 검증: 기존 테스트는 고치지 않고 기본 루프 수(코어 수)로 그대로 통과. Makefile에 tsan, tsan-test 추가 (asan-test와 같은 모양, 보고가 하나라도 있으면 실패). 새 테스트 파일 tests/multiloop_test.py에 ML-1~3 | TSan은 ASan과 같이 못 켬 → 빌드 하나 추가 |
| M9 | (2026-11-25 추가) 루프 하나마다 고정 fd가 4개(listen, epoll, 루트, 비상용. M10 뒤로는 비상용 대신 경로를 따라갈 때 잠깐 쓰는 fd) 늘어서, 기존 테스트의 fd 절대 기준(≤ 12, 상한 + 30, fd 고갈 시험의 한도 48)에 `4 × (루프 수 − 1)`을 더한다. 루프 수는 테스트가 기본값과 같은 방법으로 셈(macOS 1, Linux `os.cpu_count()`). 다른 기대값은 그대로 | 확정된 테스트 파일의 숫자를 고침. 대신 기존 테스트 전부가 기본 루프 수로 돎 |
| M10 | (2026-11-25 추가) fd 고갈 처리. ① 시작할 때 최대 연결 수를 `(fd 한도 − 고정 fd) ÷ 2`로 줄임 (설정값보다 크게는 안 함). 고정 fd = 표준 입출력 3 + 루프마다 4(listen, epoll, 루트, 경로를 따라갈 때 잠깐 쓰는 fd 1). 연결 하나는 손님 소켓 + 파일 또는 백엔드 소켓으로 최대 2. 결과가 1 미만이면 시작하지 않음(종료 코드 1). ② 비상용 fd는 없앰: 쓰려고 닫는 순간 그 번호가 프로세스 공용 칸으로 돌아가 다른 루프가 가져갈 수 있음(측정: 루프 18개 중 17개가 비상용 fd를 잃고 CPU 100%). ③ 그래도 accept가 EMFILE·ENFILE이면 그 루프만 listen 감시를 끄고 WAIT_MAX_MS(1초) 뒤에 다시 받음 | fd 한도가 낮으면 최대 연결 수가 설정보다 작아짐(시작 로그). fd가 바닥나면 대기 손님을 바로 끊지 않고 커널 줄에서 기다리게 함(전에는 하나씩 받아 끊음). 시스템 전체 fd 고갈(ENFILE)은 ①로 막지 못함 → ③으로 CPU만 보호 |

## 새 테스트 (ML)

| ID | 상황 | 기대 결과 | 결정 |
|---|---|---|---|
| ML-1 | --loops 4로 시작 | 시작 로그에 루프 4개, 정적·프록시 요청 정상 | M1, M2 |
| ML-2 | --loops 4 --max-connections 4 + 연결 5개 | 4개만 받고 5번째는 기다림. 하나를 닫으면 5번째를 받음 | M4 |
| ML-3 | --loops 4 + 여러 연결에 처리 중 요청을 걸어 둔 채 SIGINT | 처리 중 요청이 모두 끝난 뒤 종료, 종료 코드 0, 7초 안 | M6 |
