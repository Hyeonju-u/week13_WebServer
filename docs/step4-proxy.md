# 4단계: 프록시 경로 + 작은 백엔드 + 설정 파일

> 결정: 2026-11-25 대화 (Notion "웹 서버 요구분석"에 같은 내용 기록)
> 관련 R: R2a~R2e, R5a~R5c, R6a, C4 (+ 1단계 파서, 2단계 경로 정리, 3단계 이벤트 루프 재사용)
> 완료 기준 (구현 단계 계획): `/api/*`가 8001·8002로 나뉘어 가고, 백엔드를 끄거나 멈추면 502/504. 아래 테스트 목록 전부 통과, ASan 잘못된 접근 0, 3단계 테스트 그대로 통과.

## 1. 범위

- **한다:** 설정 파일, 라우터, non-blocking `connect`, 요청 전달(헤더 고치기), 백엔드 응답 받기·고치기·전달, `100 Continue`, 502/504, 최소 연결·라운드로빈, 죽은 백엔드 건너뛰기, Python 백엔드, 로그 확장
- **안 한다:** 백엔드 연결 재사용(풀), 응답 흘려보내기(D8 ②), chunked, 규칙별 접두사 떼기, GET·POST 외 메서드, 호스트 이름 백엔드, 루프 N개(5단계)

## 2. 흐름 (프록시 요청 하나)

```
헤더 완성 → parse_request_head (1단계)
  → 경로 정리: ? 자르기, % 풀기, . / .. 정리 (2단계 ①~③). 여기서 400/403이면 그 오류로 답함
  → 라우터: 정리한 경로로 규칙 찾기 (G1, G2). 없으면 정적 (3단계 그대로)
  → 프록시: POST면 Expect 처리(G7) → 본문 다 받기 (P11)
  → 백엔드 고르기 (G13, G14) → non-blocking connect (G11)
       connect 실패 → 표시 + 다음 백엔드로 (G13) / 전부 실패 → 502·504
  → 요청 보내기: 원문 경로, 헤더 고치기 (G3~G6)
  → 응답 다 받기 (G8, G9) → 헤더 고치기 (G10) → 백엔드 연결 닫기
  → 손님에게 보내기 (3단계 응답 쓰기, keep-alive 규칙 그대로)
```

진행 카드의 새 상태·전환표는 구현 쪽에서 제안하고 사람이 확인한다 (🔥 2번).

## 4. 설정 파일 항목 (G15)

```
# 예시
listen 8080
root ./www
route /api least_conn 127.0.0.1:8001 127.0.0.1:8002
max_body 1M
```

| 항목 | 기본값 | 출처 |
|---|---|---|
| `listen` | (필수) | L2 |
| `root` | (필수) | L2 |
| `route <접두사> <round_robin\|least_conn> <IP:포트>...` | 없음 (전부 정적) | G1, G2, G14 |

| `backend_fail_timeout` | 10s | G13 |

| `max_backend_response` | 8M | G9 |

| (5단계) `loops` | — | B25 |

## 5. 구현 쪽(Claude Code)에 넘길 질문

→ 2026-11-25 답함: 3-1 표 G21~G41. 구현 중 정한 것은 G42~G47.

- 진행 카드의 새 상태(본문 받기 → 백엔드 연결 중 → 요청 보내는 중 → 응답 받는 중)와 전환표, 카드에 붙일 백엔드 쪽 필드
- 백엔드 응답 버퍼를 늘리는 방식 (두 배 `realloc` / 조각 목록), 상한과의 관계
- 백엔드로 보낼 요청을 언제 만드나 (헤더 고치기를 미리 한 버퍼에 / 보내면서)
- 라우팅 규칙·백엔드 표·처리 중 수·빠진 시각을 어디에 둘지 (5단계 공유 데이터 경계 B26을 생각해서)

- 설정 파서 파일 구성, 3단계 `main`·테스트 띄우기 변경 범위, 테스트 전용 항목
- 파일 구성, Makefile 대상, 백엔드 실행 방법 (테스트·README)
