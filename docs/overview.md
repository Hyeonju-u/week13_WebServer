# C 웹서버 + 리버스 프록시 설명서

발표와 설명에 쓰는 문서입니다. 빌드와 설정은 [README](../README.md)를 봅니다.

## 한 줄 요약

C 언어와 POSIX 소켓 API만으로 만든 HTTP/1.1 웹서버입니다. 정적 파일 서빙과 리버스 프록시(경로별 백엔드 분배, Round-Robin)를 **이벤트 루프 하나**에서 처리합니다. 외부 라이브러리와 프레임워크는 쓰지 않았습니다.

우선순위는 **정확성 > 안정성 > 성능** 순입니다.

## 전체 구조

```
손님 (curl, 브라우저)
  │  HTTP 요청
  ▼
웹서버  (프로세스 1개, 스레드 1개)
  이벤트 루프  (macOS: kqueue / Linux: epoll)
  ├─ 새 연결 수락      → 연결 구조체 생성
  ├─ 읽기 가능         → HTTP 파서 → 요청이 완성되면 라우팅
  │                         ├─ 프록시 규칙에 맞음 → 백엔드로 중계 (proxy)
  │                         └─ 맞지 않음          → 정적 파일 응답 (static_file)
  ├─ 쓰기 가능         → 응답을 조금씩 전송
  └─ 타이머 힙         → 마감이 지난 연결 정리
  │
  │  (프록시 규칙에 맞는 요청만)
  ▼
백엔드 서버들  (예: 127.0.0.1:9001, 9002)
  이 프로젝트 밖의 별도 프로그램
```

| 파일 | 하는 일 |
|---|---|
| `event.c` | kqueue/epoll를 감싼 이벤트 루프. 운영체제별 코드는 여기에만 있음 |
| `http_parser.c` | 요청 문자열을 검사하며 해석. 규칙에 어긋나면 상태 코드를 정해 돌려줌 |
| `http_response.c` | 상태 줄과 헤더 조립 |
| `static_file.c` | 루트 폴더 안의 파일만 안전하게 열기 |
| `proxy_config.c` / `proxy.c` / `proxy_message.c` | 설정 읽기, 백엔드 선택과 중계, 백엔드 응답 해석 |
| `timer_heap.c` | 연결별 마감 시각을 최소 힙으로 관리 |
| `connection.c` / `server.c` | 연결 상태와 서버의 전체 흐름 |
| `buffer.c` | 늘어나는 버퍼와 전체 메모리 상한(512MB) |

## 서버가 켜지고 요청을 처리하는 순서

### A. 서버를 켤 때 (한 번)

| 번호 | 하는 일 | 어디서 |
|---|---|---|
| 1 | **옵션 읽기**: `--root`, `--port` 등. 틀리면 사용법을 출력하고 종료 | `main.c` |
| 2 | **로그 수준 전달**: 옵션에서 읽은 수준을 넘기고 `log.c`는 저장과 걸러내기만 함 | `main.c` → `log.c` |
| 3 | **종료 신호 준비**: SIGPIPE 무시, SIGINT·SIGTERM 처리기 설치 | `signals.c` |
| 4 | **프록시 규칙 파일 읽기**: `route 경로 백엔드…` 줄과 타임아웃을 읽어 메모리에 올림. 백엔드 주소는 이때 미리 숫자 주소로 바꿔 둠(요청 중에 하면 루프가 멈추므로). 틀리면 서버가 시작되지 않음 | `proxy_config.c` |
| 5 | **서버 준비** (`create_server`): 루트 폴더 열기 → fd 한도 올리기 → 이벤트 루프 → 타이머 힙 → listen 소켓 → 비상용 fd → listen 소켓을 이벤트 루프에 등록 | `server.c`, `event.c`, `timer_heap.c` |
| 6 | **시작 로그** | `main.c` |
| 7 | **이벤트 루프 실행**: 서버가 끝날 때까지 여기서 머무름. 아래 B가 이 안에서 요청마다 반복됨 | `server.c` |
| 8 | **종료 후 정리**: 자원을 해제하고 "정상 종료" 로그 | `main.c` |

프록시 규칙 파일에는 "어느 경로가 동적인지"가 따로 적혀 있지 않습니다. 요청 경로가 어떤 `route`의 접두어와 맞으면 프록시로, 어느 규칙에도 안 맞으면 정적 파일로 처리합니다(B-5).

### B. 요청마다 (A-7 안에서 반복)

| 번호 | 하는 일 | 어디서 |
|---|---|---|
| 1 | **요청 도착**: 커널이 새 연결을 알리면 이벤트 루프를 거쳐 서버가 받음 | 커널 → `event.c` → `server.c` |
| 2 | **연결 만들기, 마감 걸기**: 연결 구조체를 만들고 15초 마감을 겁니다 | `connection.c`, `timer_heap.c` |
| 3 | **데이터 쌓기**: 손님이 보낸 바이트를 입력 버퍼에 쌓음. 첫 바이트가 오면 마감이 "요청 읽기 15초"로 바뀜 | `buffer.c` |
| 4 | **요청 해석, 오류 판정**: 다 왔는지, 규칙에 맞는지 검사. 틀리면 **오류로 판정하고 상태 코드만 정함**(응답은 만들지 않음) | `http_parser.c` |
| 5 | **갈림길**: 경로가 프록시 규칙에 맞는지 찾음. 겹치면 가장 긴 경로가 이김 | `proxy_config.c` |
| 6a | **정적 파일**(규칙에 안 맞을 때): 루트 안에서 파일을 열고 Content-Type을 정하고, 응답 헤더를 직접 만듦 | `static_file.c`, `mime.c`, `http_response.c` |
| 6b | **프록시**(규칙에 맞을 때): 같은 규칙의 백엔드를 돌아가며(Round-Robin) 시작 서버로 정해 연결하고, 안 되면 다음 서버로 넘어감. 백엔드가 보낸 응답 헤더를 손질해 전달 | `proxy.c`, `proxy_message.c` |
| 7 | **출력 버퍼에 응답이 모임**: 정적 응답, 프록시 응답, 오류 응답이 모두 같은 출력 버퍼에 쌓임. 오류 응답은 4번(또는 5~6번의 실패)에서 여기로 오고 `http_response.c`가 만듦 | `buffer.c`, `http_response.c` |
| 8 | **전송, 마감 갱신**: 출력 버퍼를 조금씩 보냄. 끝나면 연결을 유지(다음 요청을 5초 기다림)하거나 닫음. 유지하면 1번의 다음 요청으로 돌아감 | `buffer.c`, `event.c`, `timer_heap.c` |

6a와 6b는 요청 하나가 둘 중 **하나만** 거칩니다. 응답을 만드는 방식도 다릅니다(정적은 서버가 처음부터, 프록시는 백엔드의 응답을 손질해서). 둘이 합쳐지는 곳은 7번의 출력 버퍼입니다.

백엔드를 고른다는 것은 "지금 살아 있는 서버를 찾는다"가 아니라 **차례대로 돌아가며 시작 서버를 정한다**는 뜻입니다. 규칙마다 `next_index`를 요청마다 1씩 올려 이번에 몇 번째 서버부터 시도할지 정하고, 연결에 실패하면 다음 서버로 넘어갑니다. 모두 실패하면 502나 504입니다. 요청을 이미 보낸 뒤의 실패는 다른 서버로 다시 보내지 않습니다.

## 왜 이벤트 루프인가 (동시성 모델)

손님마다 스레드를 만들면, 요청을 보내다 멈춘 느린 손님 하나가 스레드 하나를 통째로 붙잡습니다. 이 서버는 모든 소켓을 **non-blocking**으로 두고, 읽을 수 있는 소켓만 골라서 처리합니다.

- 느린 손님은 구조체 하나(약 320바이트)만 차지하고, 다른 손님의 처리를 막지 않습니다.
- 스레드가 하나라 잠금이 없고, 같은 입력은 항상 같은 결과를 냅니다.
- 대가: 루프 안에서 오래 기다리면 모든 손님이 멈춥니다. 그래서 `connect`는 non-blocking이고, 파일은 64KB씩 읽고, 주소 해석은 시작할 때 한 번만 합니다. CPU 코어는 하나만 씁니다.

## 정확성과 안정성을 위해 한 것

| 영역 | 내용 |
|---|---|
| HTTP 해석 | 요청 라인 8KB, 헤더 16KB·100개, 본문 1MB 상한. Host 없음·중복, 공백 오류, 잘못된 `%XX`, 제어 문자는 400/414/431/413 등으로 구분해 거절 |
| 보안 | 경로 탈출(`..`, `%2e%2e`)과 숨김 파일 차단, 심볼릭 링크 거절, 파일 열기 시 경로 조각마다 `O_NOFOLLOW`로 검사(TOCTOU 방지), 요청 밀반입(Smuggling) 방지 |
| 자원 | 연결 수 상한, 버퍼 합계 상한(넘으면 503), fd가 바닥나도 죽지 않도록 비상용 fd 하나를 미리 확보 |
| 시간 | 연결 직후 15초, 요청 읽기 15초, 유휴 5초, 백엔드 연결·응답 타임아웃을 타이머 힙으로 관리 |
| 종료 | 신호를 받으면 새 연결은 거절하고, 진행 중인 응답은 마저 보낸 뒤(최대 5초) 정상 종료 |
| 프록시 | 가장 긴 경로 우선 매칭, Round-Robin, 죽은 백엔드는 건너뜀(데이터를 보내기 전에만 재시도), hop-by-hop 헤더 제거, `X-Forwarded-For` 덮어쓰기, 손님이 응답을 느리게 받으면 백엔드 읽기를 멈춤(배압) |

## 시연 가이드: 명령어마다 무엇을 확인하는가

준비와 정리 명령은 [README의 데모 절](../README.md)에 있습니다. 여기서는 각 명령이 **무엇을 증명하는지**를 설명합니다.
서버는 `localhost:8080`, 백엔드는 9001·9002에 떠 있다고 가정합니다.

### A. 정확성

| 명령 | 확인하는 것 | 기대 결과와 의미 |
|---|---|---|
| `curl -i localhost:8080/` | **정상 경로 전체가 맞게 동작하는가.** 요청 해석 → 정적 파일 → 응답 조립 | `200 OK`와 `Content-Type: text/html`, 실제 파일 크기와 같은 `Content-Length`, `Date`, `Connection: keep-alive`. 헤더가 규격대로 붙는지 보는 기본 확인 |
| `curl -I localhost:8080/index.html` | **HEAD 요청의 의미.** HEAD는 GET과 같은 헤더를 주되 본문은 보내지 않아야 함 | `Content-Length: 156`은 GET과 같고 본문은 없음. 본문 없이 길이만 알려 주는 규칙을 지키는지 확인 |
| `curl -i --path-as-is localhost:8080/../etc/passwd` | **디렉터리 탈출(path traversal) 방어.** 루트 폴더 밖의 파일(`/etc/passwd`)을 읽을 수 있는가 | `404`. curl은 기본으로 `../`를 지워서 보내므로 `--path-as-is`로 **원본 그대로** 보내 서버가 직접 막는지 시험함. 404로 답하는 이유는 "그 파일이 있는지"조차 알려 주지 않기 위해서 |
| `curl -i localhost:8080/.git/config` | **숨김 파일 차단.** 점으로 시작하는 경로(`.git`, `.env` 등)는 실수로 올라가 있어도 노출되면 안 됨 | `404`. 실제 파일이 있어도 못 가져감 |
| `curl -i -X POST -d x=1 localhost:8080/` | **허용하지 않는 메서드 처리.** 정적 파일은 GET, HEAD만 의미가 있음 | `405 Method Not Allowed`와 `Allow: GET, HEAD`. 거절하면서 "무엇은 되는지"까지 알려 주는 규격 동작 |
| `curl -i -H "Transfer-Encoding: chunked" -H "Content-Length: 5" -d x localhost:8080/` | **요청 밀반입(HTTP Request Smuggling) 방지.** 본문 길이를 알리는 방식(`Content-Length`와 chunked)이 둘 다 오면 서버마다 해석이 갈림. 프록시와 백엔드가 다르게 읽으면, 공격자가 한 요청 안에 **숨은 두 번째 요청**을 끼워 넣을 수 있음 | `400 Bad Request`. 모호한 요청은 아예 받지 않고 연결을 닫음. 프록시가 있는 서버에서 특히 중요한 검사 |

### B. 리버스 프록시

| 명령 | 확인하는 것 | 기대 결과와 의미 |
|---|---|---|
| `for i in 1 2 3 4; do curl -s localhost:8080/api/hello; done` | **경로 라우팅과 Round-Robin.** `/api`로 시작하는 요청이 백엔드로 넘어가고, 여러 대에 번갈아 분배됨 | `backend-1, backend-2, backend-1, backend-2`. 정적 파일이 아니라 뒤쪽 서버가 답했다는 증거이기도 함 |
| `pkill -f "http.server 9001"; for i in 1 2 3; do curl -s localhost:8080/api/hello; done` | **백엔드 장애 시 우회.** 한 대가 죽었을 때 손님이 오류를 보지 않는가 | `backend-2`만 3번. 연결에 실패하면 데이터를 보내기 **전이므로** 안전하게 다음 백엔드로 재시도 |
| `pkill -f "http.server 9002"; curl -i localhost:8080/api/hello` | **전부 죽었을 때의 오류 처리.** 서버가 멈추거나 응답 없이 끊기지 않는가 | `502 Bad Gateway`. 서버는 살아 있고 손님에게 정상 형식의 오류를 돌려줌 |

### C. 동시성

| 명령 | 확인하는 것 | 기대 결과와 의미 |
|---|---|---|
| `(printf 'GET / HTTP/1.1\r\nHost: x\r\n'; sleep 8) \| nc localhost 8080` 을 5개 | **느린 손님 시뮬레이션.** 요청 마지막의 빈 줄(`\r\n\r\n`)을 보내지 않으므로 서버는 "요청이 아직 덜 왔다"고 보고 기다림. 연결 5개가 8초 동안 붙들려 있음 | 이 연결들은 서버 안에서 구조체만 차지하고 있음 |
| `curl -s -o /dev/null -w "...%{time_total}" localhost:8080/` | **느린 손님이 다른 손님을 막는가.** 위 5개가 붙어 있는 **동안** 정상 요청을 보냄 | `200`, 약 2ms. 스레드를 붙잡는 구조였다면 지연이 생길 상황인데, 이벤트 루프라 즉시 응답함. 이 시연의 핵심 |
| `wrk -t2 -c1000 -d5s --latency http://localhost:8080/index.html` | **동시 연결 1,000개를 오류 없이 처리하는가**와 처리량. wrk는 연결 1,000개를 유지하며 5초 동안 요청을 계속 보냄 | 이 개발 컴퓨터에서 약 6~7만 req/s, 중앙값 지연 약 13ms. 서버와 wrk를 같은 컴퓨터에서 돌린 수치라 절대 성능이 아니라 "연결이 많아도 안정적"이라는 확인용 |

### D. 종료

| 명령 | 확인하는 것 | 기대 결과와 의미 |
|---|---|---|
| `pkill -INT -f "build/webserver"` 후 `cat /tmp/demo/server.log` | **우아한 종료.** 종료 신호를 받았을 때 진행 중인 손님을 끊지 않는가 | 로그에 `종료 신호를 받음: 진행 중인 응답만 마저 보냄`, `정상 종료`. 새 연결은 거절하고 보내던 응답은 마저 보낸 뒤 코드 0으로 끝남 |

### 시연이 보여 주지 않는 것
아래는 시간이 길거나 환경 구성이 필요해서 **자동 테스트**로만 확인했습니다. 결과는 README의 "검증 결과"에 있습니다.

- 연결 10,000개 동시 유지, 타임아웃(15초·5초)의 정확한 시각, fd 고갈, 버퍼 상한 503, 메모리 증가 없음, 30분 장시간 실행
- 요청을 1바이트씩 쪼개서 보내기, 붙여 보낸 요청 여러 개(pipelining), 40MB 응답 전달
- 이 모든 것은 `make test`로 다시 돌릴 수 있습니다 (기능 테스트 164개, 가혹 조건 79개).
